# ROADMAP.md — Роадмап UI/UX мобильного приложения Univer

> Роадмап построения мобильного клиента (React Native) поверх готового бэкенда
> [`coungard/univer`](https://github.com/coungard/univer). Все эндпоинты и DTO ниже — из `API.md`
> этого репозитория; флоу авторизации — из `MOBILE.md` бэкенд-репозитория. Роадмап не придумывает
> функциональность, которой нет на бэкенде — там, где бэкенд чего-то не позволяет, это явно отмечено.

---

## 1. Обзор и допущения

- Бэкенд полностью реализован: 14 доменных модулей, REST API `/api/v1/...`, авторизация через
  Keycloak (`univer-realm`), роли `ADMIN` / `TEACHER` / `STUDENT` (плюс заведённые, но нигде не
  проверяемые API `APPLICANT`/`GUEST`).
- Мобильный проект сейчас — чистый scaffold `@react-native-community/cli` (RN 0.86, React 19.2):
  навигации, HTTP-слоя, auth и дизайн-системы ещё нет.
- Приложение — обычный REST-клиент того же Keycloak-realm, что и веб; отдельный BFF не нужен.

### ⚠️ Ключевое ограничение бэкенда: нет self-service выбора группы

`RegisterStudentRequest` принимает `universityId`, но **не** `groupId`. Поле `groupId` в
`StudentDto` выставляется только администратором через `PUT /students/{id}`. Значит:

- **Университет** — реальный self-service шаг: студент выбирает его при регистрации
  (`GET /universities` → выбор → `RegisterStudentRequest.universityId`).
- **Группа** — не выбирается пользователем в приложении. После регистрации студент попадает в
  состояние «профиль создан, группа ещё не назначена», и должен явно видеть пустой экран с этим
  статусом, а не форму выбора группы. `GET /lectures/me` в этом состоянии просто вернёт пустую
  страницу (не ошибку) — это тоже нужно обработать как «нет расписания, ждите назначения группы»,
  а не как баг.
- Самостоятельное присоединение к группе (например, по инвайт-коду) — потенциальное расширение
  бэкенда, вне скоупа текущего API и этого роадмапа.

## 2. Технический стек

| Область | Библиотека | Почему |
|---|---|---|
| Навигация | `@react-navigation/native` + `native-stack` + `bottom-tabs` | стандарт де-факто для RN |
| Серверное состояние/кэш | `@tanstack/react-query` | готовые паттерны под пагинацию `Page<T>` из `API.md`, retry, инвалидация кэша после мутаций |
| Локальное состояние (auth, сессия) | `zustand` | лёгкий стор без boilerplate Redux |
| Авторизация (PKCE) | `react-native-app-auth` | Authorization Code + PKCE через системный браузер (Custom Tabs / ASWebAuthenticationSession) — `MOBILE.md` явно требует не-WebView |
| Хранение токенов | `react-native-keychain` | Keychain (iOS) / Keystore-backed EncryptedSharedPreferences (Android), как требует `MOBILE.md` |
| HTTP-клиент | `axios` + интерцептор на `401` → тихий refresh (`grant_type=refresh_token`) | единая точка для обработки таблицы ошибок `400/401/403/404/422` из `API.md` |
| Формы/валидация | `react-hook-form` + `zod` | регистрация студента/преподавателя, admin CRUD-формы |
| UI-кит | `react-native-paper` | Material-компоненты «из коробки», быстрый старт дизайн-системы |
| Расписание/таймтейбл | кастомный компонент `WeeklyTimetable` | под модель `Pair`/`WeekParity`/`dayOfWeek` готовой библиотеки один-в-один нет — проще и надёжнее написать свою сетку |
| Тесты | Jest (уже настроен в проекте) + `@testing-library/react-native` | соответствует существующему `jest.config.js` |

**Риск:** RN 0.86 + React 19.2 — очень свежие версии. Перед установкой (особенно
`react-native-app-auth`, который тянет нативный код) проверить актуальную поддержку этих версий и
при необходимости — альтернативу (`expo-auth-session`, если проект решит перейти на Expo, либо
ручная реализация PKCE-флоу через `react-native-inappbrowser-reborn` + `axios`).

### Структура папок (рекомендация)

```
src/
  api/            # axios-инстанс, генерация типов из DTO API.md, обработка ошибок
  auth/           # PKCE-флоу, keychain, auth-стор (zustand)
  navigation/     # RootNavigator, стек по ролям (Student/Teacher/Admin)
  features/
    schedule/     # недельное расписание, лекции
    courses/      # список курсов, детали
    attendance/   # посещаемость (студент и преподаватель)
    profile/      # профиль пользователя
    onboarding/   # регистрация, выбор университета, ожидание группы
    teacher/      # модуль преподавателя
    admin/        # CRUD-модуль администратора
  components/     # общие UI-компоненты (карточки, пустые состояния, лоадеры)
  store/          # общие zustand-сторы
```

## 4. Фазы разработки

Каждая фаза = цель + экраны + эндпоинты `API.md` + критерий готовности. Фазы 0–5 — ядро продукта
(Student-first, MVP), 6–7 — роли Teacher/Admin, 8 — полировка.

### Фаза 0 — Фундамент ✅ готово
- [x] Инициализация навигации (`RootNavigator`: `AuthStack` / `AppStack` по ролям).
- [x] Дизайн-система: тема `react-native-paper`, базовые компоненты (кнопка, карточка, пустое
  состояние, лоадер, тост ошибки).
- [x] HTTP-слой: `axios`-инстанс с базовым URL, интерцептор на `Authorization: Bearer`, единый
  обработчик ошибок по таблице `API.md` (`400` → поле→сообщение, `401` → refresh или логаут,
  `403` → экран «нет доступа», `404`/`422` → **не полагаться на поля `error`/`path`**, только на
  `status`/`message`).
- [x] Env-конфиг: `auth-server-url`, `client_id=univer-mobile`, `redirect_uri=univer://auth/callback`,
  `logout_redirect_uri=univer://auth/logout`, `api-base-url`.
- [x] **Готово, когда:** пустой app-shell собирается на Android/iOS, навигация между заглушками
  `AuthStack`/`AppStack` работает, есть рабочий axios-клиент с моками.

### Фаза 1 — Авторизация ✅ готово
- [x] Сплэш-экран с восстановлением сессии (проверка refresh-токена в keychain).
- [x] Экран логина: кнопка «Войти» открывает системный браузер, PKCE-флоу через
  `react-native-app-auth`, приём `univer://auth/callback`.
- [x] Логаут: revoke + редирект на `univer://auth/logout`, очистка keychain.
- [x] Регистрация студента: форма (`username`, `firstname`, `lastname`, `fullname`, `email`,
  `password`, `enrollmentDate`, выбор университета из `GET /universities`) →
  `POST /students/register` (публичный эндпоинт). Обработка `409` (email занят).
- [x] Регистрация преподавателя: аналогичная форма с выбором кафедры (`GET /departments/...`) →
  `POST /teachers/register`. **Не использовать `POST /teachers/` для регистрации** — этот путь не
  привязан к Keycloak.
- [x] Тихий refresh access-токена по истечении, экран ошибки Keycloak (недоступен auth-сервер и т.п.).
- [x] **Готово, когда:** можно зарегистрироваться, войти, выйти, приложение переживает рестарт с
  валидной сессией.

### Фаза 2 — Онбординг после регистрации
- [ ] Экран «профиль создан» → если `groupId == null`, показать пустое состояние «группа ещё не
  назначена, обратитесь к администратору» вместо расписания.
- [ ] Read-only просмотр своего университета/факультета/программы (по доступным `GET`-эндпоинтам).
- [ ] **Готово, когда:** новый студент без группы не видит ошибок — только понятное пустое состояние;
  как только admin назначает группу (внешний процесс), при следующем открытии приложение
  показывает расписание без доп. действий пользователя.

### Фаза 3 — Главный профиль и расписание (ядро продукта)
- [ ] Таб «Профиль»: данные из `StudentDto`/`TeacherDto` (ФИО, email, университет/кафедра, дата
  зачисления/должность).
- [ ] Таб «Расписание»: `WeeklyTimetable` на основе `GET /lectures/me` (уже отсортировано по
  `scheduledTime`) — сетка день × номер пары, переключение недель с учётом `weekParity`, выделение
  текущего дня, pull-to-refresh.
- [ ] Пустое состояние, если лекций нет (в т.ч. случай «нет группы» из Фазы 2).
- [ ] **Готово, когда:** студент видит своё расписание на неделю вперёд/назад, тянет вниз для
  обновления.

### Фаза 4 — Лекции и курсы
- [ ] Экран деталей лекции: `title`, `content`, `room`, `teacherId` → имя преподавателя, время начала/
  окончания, длительность.
- [ ] Список курсов (`GET /courses`, `GET /courses/department/{id}`), карточка курса с описанием.
- [ ] Переход из ячейки расписания в детали лекции и в карточку курса.
- [ ] **Готово, когда:** от таба «Расписание» можно дойти до полной информации о занятии и курсе за 1
  тап.

### Фаза 5 — Посещаемость (студент)
- [ ] Своя статистика по курсу: `GET /attendance/student/{id}/course/{courseId}/stats`

- [ ] История отметок: `GET /attendance/student/{id}`.
- [ ] **Готово, когда:** на карточке курса студент видит процент посещаемости и историю по лекциям.

### Фаза 6 — Модуль преподавателя
- [ ] «Мои курсы» (`GET /courses` с фильтром на своего `teacherId`, либо `GET /courses/department/{id}`

- [ ] «Мои лекции»: список + создание вручную (`POST /lectures`), генерация одной лекции из шаблона

  (`POST /lectures/generate/semester/{weekScheduleCycleId}` — идемпотентно, безопасно вызывать
  повторно).
- [ ] Отметка посещаемости по лекции: ростер группы(групп) лекции + чекбоксы →
  `POST /attendance` (`LectureAttendanceDto`); ошибка `422`, если студент не `ACTIVE` в зачислении
  на курс — показать понятное сообщение, а не «неизвестная ошибка».
- [ ] Статистика по лекции: `GET /attendance/lecture/{lectureId}/stats`.
- [ ] **Готово, когда:** преподаватель может сгенерировать лекции на семестр и отметить посещаемость на

### Фаза 7 — Модуль администратора
Самый тяжёлый по объёму модуль — приоритизировать по факту необходимости, возможно после MVP.
- [ ] CRUD-экраны: University, Faculty, Department, Program, StudyYear, Semester, Group,
  BellScheduleEntry, Pair, WeekScheduleCycle (список + форма создания/редактирования + удаление).
- [ ] Массовое зачисление группы на курс: `POST /enrollments/group/{groupId}/course/{courseId}`.
- [ ] Назначение студента в группу: `PUT /students/{id}` — единственный способ закрыть «дыру» из

- [ ] ⚠️ В UI явно скрывать create/update/delete для Faculties/Departments/части Programs от
  не-`ADMIN`-пользователей, даже если по API это технически разрешено любой роли (см. «Открытые
  вопросы» `API.md` — это похоже на недосмотр бэкенда, а не сознательное решение, полагаться на это
  на клиенте не стоит).
- [ ] **Готово, когда:** администратор может завести университет → факультет → кафедру → программу →

  инструментам.

- [ ] Push-уведомления и оффлайн-кэш — явно вне скоупа `MOBILE.md` бэкенд-команды на данный момент;

## 5. Чек-лист особенностей API, которые должны быть учтены в UI

- `404`/`422` — поле `path` всегда `"/"` либо отсутствует, `error` для `422` всегда `"Not Found"` —
  определять контекст ошибки на клиенте по тому, какой запрос упал, не по телу ответа.
- `GET /students/{id}` не проверяет, что `id` совпадает с `sub` вызывающего токена — не давать
  обычному пользовательскому UI возможность подставлять произвольный `id` (например, не строить
  экран «профиль студента по ID» вне admin-модуля).
- `POST /teachers/` (без `/register`) не привязан к Keycloak — использовать только
  `POST /teachers/register` для регистрации преподавателя.
- `POST /lectures/generate/semester/{id}` идемпотентен — можно смело давать повторный тап «сгенерировать» в UI преподавателя без риска дублей.
- `GET /lectures/me` на пустой группе возвращает пустую страницу, а не ошибку — обрабатывать как
  «нет расписания», не как сбой сети.
