# UI_UX.md — генерация расписания/лекций «на ходу»

> Черновик от Claude: структура документа + рекомендации по UX для ключевой фичи продукта —
> генерация `Lecture` из шаблонов `Pair`. Разделы «Рекомендации» — предложения, разделы
> «Ожидаемое поведение» — здесь **владелец продукта описывает финальное решение**; там, где решение
> ещё не принято, оставлен явный вопрос вместо предположения.

---

## 1. Контекст: что вообще «генерируется»

Бэкенд различает две сущности (см. `API.md:104-136`, разобрано в чате этой сессии):

- **`Pair`** — шаблон повторяющегося занятия в циклическом расписании семестра (`WeekScheduleCycle`):
  день недели + чётность недели (`ODD`/`EVEN`/`BOTH`) + номер пары + курс + преподаватель + аудитория +
  группы. Это «расписание» в привычном понимании деканата — таблица «когда и что».
- **`Lecture`** — конкретное занятие на конкретную дату/время. Это то, что видит студент
  (`GET /lectures/me`) и то, по чему отмечается посещаемость.

Между ними нет автосвязи. `Lecture` появляются только явным действием:

| Действие | Эндпоинт | Свойства |
|---|---|---|
| Одна лекция на одну дату из шаблона | `POST /lectures/generate` (`GenerateLectureRequest{pairId, date}`) | `date` должна соответствовать `dayOfWeek`/`weekParity` пары |
| Весь семестр разом | `POST /lectures/generate/semester/{weekScheduleCycleId}` | генерирует по всем `Pair` цикла в границах `Semester.startDate…endDate`; **идемпотентно** — уже сгенерированная пара `Pair+дата` молча пропускается, повторный вызов безопасен |
| Вручную, без шаблона | `POST /lectures` (`LectureDto`) | `sourcePairId` не заполняется — полностью ручное занятие (замена, доп. пара, отработка) |
| Редактирование/отмена одной лекции | `PUT /lectures/{id}` / `DELETE /lectures/{id}` | точечная правка после генерации |

«Генерация на ходу» в терминах продукта = преподаватель/админ в любой момент семестра нажимает
кнопку и превращает шаблон `Pair` в реальные занятия в расписании студентов — без ручного ввода
каждой даты.

## 2. Роли и точки входа

Из `ROADMAP.md` Фазы 6–7: `POST /generate*` доступны `ADMIN`/`TEACHER`.

**Рекомендация:** развести UX по ролям, а не давать один и тот же экран:

- **Teacher** — генерирует только для *своих* `Pair` (по `teacherId`). Точка входа — из своего
  расписания/списка курсов, контекст уже сужен до «мои занятия».
- **Admin** — генерирует для любого `WeekScheduleCycle`/`Pair` в системе. Точка входа — из
  справочника `WeekScheduleCycle` (Фаза 7), с выбором семестра/группы явно.

**Ожидаемое поведение (заполнить):**
- _Может ли Teacher генерировать за другого преподавателя (замещение)?_
- _Нужен ли Admin отдельный «массовый» режим (сразу для нескольких циклов/групп), или всегда один `weekScheduleCycleId` за раз, как позволяет API?_

## 3. Принципы UX для генерации (рекомендации)

1. **Предпросмотр перед коммитом.** Bulk-генерация на весь семестр — необратимое по объёму
   действие (десятки-сотни `Lecture` для сотен студентов). Перед вызовом
   `POST /generate/semester/{id}` показать сводку: диапазон дат семестра, число `Pair` в цикле,
   оценочное число лекций (`Pair.count × число недель × 1`, с поправкой на `ODD`/`EVEN`), список
   затронутых групп/курсов. Кнопка «Сгенерировать» — осознанное действие, а не побочный эффект
   захода на экран.
2. **Явно сообщать про идемпотентность.** Раз повторный вызов безопасен (API.md:326-327) — снять
   тревожность «а вдруг задвою». В экране результата отдельно показывать: «создано N новых»,
   «пропущено M — уже существовали» (если бэкенд возвращает достаточно данных для дельты; если
   `POST` отдаёт только итоговый `LectureDto[]` без флага «новая/пропущена», дельту считать
   на клиенте: сравнить с ранее закэшированным списком лекций цикла до вызова).
3. **Генерация — не финальное состояние, а стартовая точка.** После bulk-генерации преподаватель
   должен иметь возможность точечно скорректировать результат: перенести/отменить одно занятие
   (`PUT`/`DELETE /lectures/{id}`), добавить внеплановое (`POST /lectures` без `pairId`). Экран
   «мои лекции» — единый список, где сгенерированные (`sourcePairId != null`) и ручные записи
   визуально помечены (иконка/бейдж «по шаблону» vs «вручную»), но управляются одинаково.
4. **Точечная генерация — инструмент для края семестра, не основной путь.** `POST /generate` (одна
   дата) нужен для случаев «пара была, потом добавили новую группу в середине семестра» или
   «отработка пропущенного занятия». В UI — вторичное действие («Добавить занятие по шаблону на
   дату»), а не альтернатива основной кнопке «Сгенерировать семестр».
5. **Прогресс и ошибки.** `generate/semester` — потенциально небыстрый запрос (сотни записей).
   Показать индикатор ожидания с понятным текстом («Генерируем расписание, это может занять
   несколько секунд»), а не просто спиннер на пустом экране. При сетевой ошибке — состояние
   «не удалось сгенерировать, попробовать снова» с кнопкой ретрая (благодаря идемпотентности повтор
   безопасен всегда, это стоит явно сказать пользователю в тексте ошибки).
6. **Видимость для студента без пуш-уведомлений.** Push вне скоупа (`ROADMAP.md` Фаза 8). Значит
   единственный сигнал студенту — то, что он увидит при следующем открытии/pull-to-refresh таба
   «Расписание» (уже реализовано в Фазе 3). **Ожидаемое поведение (заполнить):** нужно ли
   визуально выделять «новые с прошлого раза» лекции в расписании студента (например, через
   локально сохранённый timestamp последнего просмотра), или это избыточно для MVP?

## 4. Предлагаемый флоу экранов (Teacher, Фаза 6)

```
Мои курсы → Курс → «Расписание курса» (список Pair цикла)
                          │
                          ├─ [Сгенерировать на семестр] → Предпросмотр → Подтверждение → Результат
                          │                                                   (N создано / M пропущено)
                          │
                          └─ Pair → [Сгенерировать одну дату] → выбор даты (валидна по dayOfWeek/weekParity)
                                                                       → создана Lecture

Мои лекции (плоский список, все сгенерированные + ручные)
     │
     ├─ Lecture → [Редактировать] (room/time/content) → PUT
     ├─ Lecture → [Отменить занятие] → DELETE (с подтверждением)
     └─ [+ Добавить занятие вручную] → POST /lectures (sourcePairId не задан)
```

**Ожидаемое поведение (заполнить):**
- _Где физически живёт кнопка «Сгенерировать на семестр» — на экране курса, цикла, или отдельный
  раздел «Расписание» в модуле преподавателя?_
- _Что показываем, если у `WeekScheduleCycle` вообще нет `Pair` (пустой цикл) — блокируем кнопку
  генерации или даём нажать и получить пустой результат?_
- _Нужна ли отмена долгой генерации (если запрос идёт много секунд)?_

## 5. Пустые/промежуточные состояния (студент)

Уже частично реализовано в `src/features/schedule/ScheduleScreen.tsx`:
- нет группы → «группа ещё не назначена, обратитесь к администратору»;
- есть группа, лекций нет → «для вашей группы ещё не сгенерированы занятия, загляните позже».

**Ожидаемое поведение (заполнить):**
- _Второе сообщение сейчас звучит пассивно («загляните позже»). Нужно ли что-то более активное —
  например, дата ближайшего ожидаемого обновления, или контакт для вопроса? Или текущая формулировка
  устраивает?_
- _Частичная генерация: если сгенерирована только часть семестра (например, только для одной группы
  из нескольких в `Pair.groupIds`, либо только начало семестра через точечный `generate`), как
  студент должен понимать, что расписание неполное, а не «уже всё»? API не даёт признака
  «расписание на семестр полностью сгенерировано» — это состояние придётся выводить эвристически
  на клиенте (например, сравнивать последнюю дату лекции с `Semester.endDate`) либо явно
  зафиксировать как ограничение, с которым живём в MVP._

## 6. Открытые вопросы (требуют решения перед реализацией)

- [ ] Может ли Teacher генерировать за другого преподавателя?
- [ ] Нужен ли Admin отдельный массовый режим по нескольким циклам сразу?
- [ ] Как считать и показывать дельту «создано/пропущено» при отсутствии этого поля в ответе API?
- [ ] Нужна ли визуальная отметка «новых» лекций в расписании студента?
- [ ] Где в UI преподавателя живёт точка входа в генерацию?
- [ ] Поведение при пустом `WeekScheduleCycle` (без `Pair`)?
- [ ] Нужна ли отмена долгой генерации?
- [ ] Как сообщать студенту о неполном (частично сгенерированном) расписании?
- [ ] Что происходит при `DELETE /lectures/{id}`, если по лекции уже есть отметки посещаемости
  (`LectureAttendance`) — бэкенд это не описывает отдельно в `API.md`, нужно уточнить поведение
  или добавить клиентское предупреждение «по этому занятию есть отметки посещаемости».
