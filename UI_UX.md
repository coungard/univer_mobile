# UI_UX.md — генерация расписания/лекций «на ходу»

> Черновик от Claude: структура документа + рекомендации по UX для ключевой фичи продукта —
> генерация `Lecture` из шаблонов `Pair`. Разделы «Рекомендации» — предложения, разделы
> «Ожидаемое поведение» — здесь **владелец продукта описывает финальное решение**; там, где решение
> ещё не принято, оставлен явный вопрос вместо предположения.
>
> Цель продукта — чтобы **студент сам** заполнял циклическое расписание своей группы (`Pair`) и
> генерировал по нему `Lecture`, без участия `ADMIN`/`TEACHER` на каждом шаге. Это прямо
> конфликтовало с бэкендом на момент написания документа (раздел 0 ниже) — решение было
> зафиксировано как требование к бэкенд-команде. Блокер снят: реализовано и смёржено в `master`
> `coungard/univer` (PR [#65](https://github.com/coungard/univer/pull/65),
> [#66](https://github.com/coungard/univer/pull/66), [#67](https://github.com/coungard/univer/pull/67),
> [#68](https://github.com/coungard/univer/pull/68); трекинг — issue
> [#63](https://github.com/coungard/univer/issues/63), закрыт). `API.md` синхронизирован.

## 0. ✅ Блокер снят — бэкенд расширил RBAC

**Права `STUDENT` теперь:**

| Действие | Скоуп для `STUDENT` |
|---|---|
| `POST`/`PUT`/`DELETE /pairs` | Только пары, где `groupIds` = **ровно** его собственная группа (не поток на несколько групп); только пока цикл в статусе `DRAFT` |
| `POST /lectures/generate` | Только для `Pair` своей группы |
| `POST /lectures/generate/semester/{id}` | По всем `Pair` цикла, но фильтруется до `Pair` своей группы — чужие `Pair` того же цикла молча пропускаются |
| `POST /week-schedule-cycles` | **По-прежнему только `ADMIN`** — ровно как рекомендовано в исходной постановке вопроса: один `WeekScheduleCycle` на семестр (`422` при дубле, `API.md:112`), создаёт его `ADMIN` разово при открытии семестра. Self-service `get-or-create` не реализован (issue #63) — отдельный запрос к бэкенд-команде, если понадобится. |

Это в точности реализует минимальный скоуп, который был предложен в исходной постановке, и
закрывает оба пункта, которые были под вопросом:

- **Конфликты teacher/room между группами одного цикла** (issue #62, PR #68) — решено на
  бэкенде: `POST`/`PUT /pairs` проверяет пересечение по дню недели + чётности недели + времени, и
  если совпадает `teacherId` или `room` с уже существующей парой **того же цикла** — `422`,
  блокирующая ошибка, действует для всех ролей, включая `ADMIN` (`API.md:303-308`).
- **`generate/semester` генерировал по всем `Pair` цикла, а не только по группе** (issue #61,
  PR #67) — решено без нового параметра/эндпоинта: для `STUDENT` эндпоинт сам фильтрует до `Pair`
  его группы (у студента всегда ровно одна группа); `Pair` других групп цикла пропускаются молча,
  не ошибка (`API.md:359-364`).
- **`Pair`-доступ `STUDENT`** (issue #60, PR #66) — со скоупом «ровно своя группа» (`API.md:294-302`).

**Новое, чего не было в исходном запросе — статус согласования цикла.** `WeekScheduleCycle`
получил поле `status: DRAFT | AGREED` (`API.md:108-114`): новый цикл всегда создаётся в `DRAFT`,
`Pair` внутри него можно редактировать (`ADMIN` или `STUDENT` своей группы); `ADMIN` переводит цикл
в `AGREED` (`PUT /week-schedule-cycles/{id}/status`, `API.md:256,261-264`, `ADMIN`-only, переход
обратим в обе стороны) — после этого `Pair` правит только `ADMIN`, даже для своей группы. Генерацию
`Lecture` статус цикла **не ограничивает** — генерировать можно и из `AGREED`, и из `DRAFT` цикла.
Это даёт естественную точку «расписание согласовано, дальше не трогаем» — отражено в UI ниже
(разделы 4, 6).

Также обнаружено по факту реализации (учтено в форме заполнения `Pair`, раздел 4):
- `dayOfWeek` де-факто ограничен `MONDAY`…`FRIDAY` (`API.md:120-122`) — `SATURDAY`/`SUNDAY`
  отклоняется `422`.
- `POST /lectures/generate` (точечная генерация, одна дата) **не идемпотентен** (`API.md:353-358`)
  — повторный вызов на уже занятую пару+дату вернёт `422`, а не тихий пропуск (в отличие от
  `generate/semester`). Это не входило в исходный блокер, но обнаружилось по ходу реализации —
  учтено как факт поведения, а не открытый вопрос.

## 1. Контекст: что вообще «генерируется»

Бэкенд различает две сущности (см. `API.md`, разделы `WeekScheduleCycles`/`Pairs`/`Lectures`):

- **`Pair`** — шаблон повторяющегося занятия в циклическом расписании семестра (`WeekScheduleCycle`):
  день недели (пн–пт) + чётность недели (`ODD`/`EVEN`/`BOTH`) + номер пары + курс + преподаватель +
  аудитория + группы.
- **`Lecture`** — конкретное занятие на конкретную дату/время. Это то, что видит студент
  (`GET /lectures/me`) и то, по чему отмечается посещаемость.

Между ними нет автосвязи. `Lecture` появляются только явным действием:

| Действие | Эндпоинт | Свойства |
|---|---|---|
| Одна лекция на одну дату из шаблона | `POST /lectures/generate` | `date` должна соответствовать `dayOfWeek`/`weekParity` пары; **не идемпотентно** — повтор на существующую пару+дату даёт `422` |
| Весь семестр разом | `POST /lectures/generate/semester/{weekScheduleCycleId}` | идемпотентно (дубли молча пропускаются); для `STUDENT` — только по `Pair` своей группы |
| Вручную, без шаблона | `POST /lectures` (`ADMIN`/`TEACHER`) | `sourcePairId` не заполняется — замена, доп. пара, отработка |
| Редактирование/отмена одной лекции | `PUT`/`DELETE /lectures/{id}` (`ADMIN`/`TEACHER`) | точечная правка после генерации |

«Генерация на ходу» = студент в любой момент семестра (пока цикл в `DRAFT`) заполняет `Pair` своей
группы и одним действием превращает его в реальные занятия — без ручного ввода каждой даты и без
похода к администратору.

## 2. Роли и точки входа

| Роль | Что делает | Скоуп |
|---|---|---|
| **Student** (основной сценарий) | Заполняет `Pair` своей группы, пока цикл в `DRAFT`; генерирует `Lecture` по этим `Pair` | Только своя группа, только `DRAFT`-цикл |
| **Teacher** | То же, но по своим курсам (`teacherId`) — подстраховка, если группа не заполнила расписание сама | Свои `Pair` (по `teacherId`), без ограничения по статусу цикла |
| **Admin** | Создаёт `WeekScheduleCycle` на семестр; переключает `DRAFT`⇄`AGREED`; правит/удаляет любой `Pair` в любом статусе; разруливает конфликты, которые не смог создать студент (бэкенд их уже не пропустит — см. раздел 0) | Без ограничений |

**Ожидаемое поведение (заполнить):**
- _Заполняет расписание **любой** студент группы, или обычно один и тот же человек? Бэкенд это не
  ограничивает — любой студент с `groupId`, совпадающим с группой пары, может её редактировать;
  конкурентные правки — `PUT` последнего вызова побеждает (last-write-wins), явной блокировки
  «уже редактируется другим» нет._
- _Кто и когда переводит цикл в `AGREED`? Автоматически (например, за N дней до начала семестра),
  вручную администратором по своему решению, или по запросу от старосты/студента? Как студенты
  узнают о переходе — баннер/пуш, или просто ловят `422` при попытке сохранить?_

## 3. Принципы UX для генерации (рекомендации)

1. **Предпросмотр перед коммитом.** Перед вызовом генерации на семестр показать сводку: диапазон
   дат семестра, число заполненных студентом `Pair`, оценочное число лекций. Кнопка
   «Сгенерировать» — осознанное действие.
2. **Явно сообщать про идемпотентность там, где она есть — и предупреждать там, где её нет.**
   `generate/semester` безопасно вызывать повторно (лишнее в UI можно так и подписать). Точечный
   `POST /generate` **не идемпотентен** — повторный клик на уже сгенерированную дату должен либо
   быть недоступен в UI (кнопка дизейблится, если для этой пары+даты уже есть `Lecture`), либо
   показывать понятную ошибку «занятие на эту дату уже создано», а не сырой `422`.
3. **Заполнение — обычный CRUD-экран, не мастер на один раз.** Список `Pair` своей группы —
   редактируемая таблица «день × номер пары», доступная, пока цикл в `DRAFT`.
4. **Конфликты teacher/room — реальная блокирующая ошибка бэкенда, не просто совет клиента.**
   `POST`/`PUT /pairs` вернёт `422` с текстом, включающим ID и время конфликтующей пары — показать
   это как понятную ошибку формы («Преподаватель уже занят в это время — пара `…`, пн 10:00–11:30»),
   а не общий «Не удалось сохранить». Отдельная клиентская пред-валидация не обязательна — бэкенд
   всё равно перепроверит при сохранении, — но может ускорить обратную связь, если у клиента уже
   загружены все `Pair` цикла.
5. **Явно показывать статус цикла (`DRAFT`/`AGREED`).** Пока `DRAFT` — форма редактирования активна
   для студента. Как только `AGREED` — кнопки «Изменить»/«Удалить»/«+ Добавить» у студента скрыть
   или задизейблить с пояснением «расписание согласовано, обратитесь к администратору», а не просто
   ловить `422` по клику.
6. **Генерация — отдельный явный шаг после заполнения**, не автоматический побочный эффект
   сохранения `Pair`.
7. **Прогресс и ошибки.** `generate/semester` — потенциально небыстрый запрос. Показать индикатор
   ожидания с понятным текстом, а не спиннер на пустом экране.

## 4. Флоу «Студент сам заполняет расписание» (основной сценарий)

```
Таб «Расписание» (пусто, группа назначена, лекций нет)
     │
     ├─ Цикл на семестр не создан (GET /week-schedule-cycles/semester/{semesterId} → 404)
     │     → пустое состояние «расписание семестра ещё не открыто администратором,
     │        обратитесь к администратору» (блокер вне контроля студента)
     │
     ├─ Цикл существует и в AGREED, Pair моей группы нет
     │     → пустое состояние «расписание группы ещё не заполнено и уже согласовано —
     │        обратитесь к администратору» (окно самостоятельного заполнения закрыто)
     │
     └─ Цикл существует и в DRAFT, Pair моей группы нет
           → CTA «Заполнить расписание группы»
                 │
                 ▼
        Экран «Расписание группы» (бейдж статуса цикла: «Черновик» / «Согласовано») —
        таблица день недели (пн–пт) × номер пары, только Pair моей группы
                 │
                 ├─ [+ Добавить занятие] (доступно только в DRAFT) → форма:
                 │     день недели (пн–пт), чётность (ODD/EVEN/BOTH), номер пары,
                 │     курс, преподаватель (авто из Course.teacherId), аудитория,
                 │     время (по умолчанию из BellScheduleEntry университета)
                 │     → POST /pairs
                 │     → 422 «конфликт с парой N (день, время)» — показать инлайн у поля
                 │
                 ├─ Pair → [Изменить] (доступно только в DRAFT) → PUT /pairs/{id}
                 ├─ Pair → [Удалить] (доступно только в DRAFT) → DELETE /pairs/{id}
                 │
                 └─ [Сгенерировать занятия на семестр] (доступно всегда, даже в AGREED —
                    статус цикла не ограничивает генерацию, только редактирование Pair;
                    активно, когда заполнена хотя бы одна пара)
                    → предпросмотр (сколько своих Pair, диапазон дат)
                    → подтверждение → POST /lectures/generate/semester/{cycleId}
                    → результат: «Готово, расписание появится в разделе
                       “Расписание” у всех студентов группы» (только по своим Pair —
                       чужие Pair цикла не затрагиваются, скоуп уже на бэкенде)
```

**Ожидаемое поведение (заполнить):**
- _Курс для `Pair.courseId` — студент выбирает из **всех** курсов кафедры/университета
  (`GET /courses`), или только из тех, на которые уже есть зачисление у кого-то из группы
  (`Enrollment`)? Если из всех — где в UI ограничение, чтобы студент случайно не завёл занятие по
  курсу, на который никто не зачислен?_
- _Разрешаем ли студенту переопределять `startTime`/`endTime` пары вручную, или всегда наследуем
  из `BellScheduleEntry` по `pairNumber`?_

## 5. Флоу Teacher/Admin (вторичный путь, правка и подстраховка)

```
Мои курсы → Курс → «Расписание курса» (список Pair цикла, включая заведённые студентами)
                          │
                          ├─ [Сгенерировать на семестр] → Предпросмотр → Подтверждение → Результат
                          │     (для Teacher/Admin — по всем Pair цикла, без фильтра по группе)
                          │
                          └─ Pair → [Сгенерировать одну дату] → выбор даты
                                                                       → создана Lecture

Мои лекции (плоский список, все сгенерированные + ручные)
     │
     ├─ Lecture → [Редактировать] (room/time/content) → PUT
     ├─ Lecture → [Отменить занятие] → DELETE (с подтверждением)
     └─ [+ Добавить занятие вручную] → POST /lectures (sourcePairId не задан)

Admin: экран цикла семестра
     │
     └─ [Согласовать расписание] (DRAFT → AGREED) / [Вернуть в черновик] (AGREED → DRAFT)
          → PUT /week-schedule-cycles/{id}/status
```

## 6. Пустые/промежуточные состояния (студент)

| Состояние | Причина | Что показываем |
|---|---|---|
| Нет группы | `student.groupId == null` | «группа ещё не назначена, обратитесь к администратору» |
| Есть группа, цикла семестра нет | `GET /week-schedule-cycles/semester/{semesterId}` → 404 | «расписание семестра ещё не открыто, обратитесь к администратору» |
| Цикл в `AGREED`, `Pair` моей группы нет | группа не успела заполнить расписание до согласования | «расписание группы не заполнено и уже согласовано — обратитесь к администратору» (без CTA на заполнение) |
| Цикл в `DRAFT`, `Pair` моей группы нет | группа ещё не заполнила | CTA «Заполнить расписание группы» (раздел 4) |
| `Pair` заполнены, `Lecture` нет | генерация ещё не запускалась | CTA «Сгенерировать занятия на семестр» прямо в табе «Расписание» |
| `Pair` заполнены частично относительно `Semester.endDate` | последняя `Lecture` раньше конца семестра, а `Pair` покрывают более поздние даты | баннер «расписание могло измениться — перегенерировать?» (эвристика на клиенте, бэкенд не даёт признака «актуальности») |

## 7. Открытые вопросы

Бэкенд-блокеры из исходной постановки (раздел 0) сняты — все три пункта (`Pair`-доступ `STUDENT`
issue #60/PR #66, скоуп `generate/semester` issue #61/PR #67, конфликты teacher/room issue #62/PR #68)
реализованы и смёржены (трекинг issue #63). Ниже — то, что осталось на решение продукта.

- [ ] Любой студент группы или только представитель («староста») может редактировать расписание
  группы? Технических ограничений на бэкенде нет — это чисто продуктовое/социальное соглашение.
- [ ] Кто и когда переводит цикл `DRAFT` → `AGREED`, и как студенты об этом узнают (баннер/пуш, или
  просто ловят `422` при попытке сохранить)?
- [ ] Источник списка курсов при заполнении `Pair` — все курсы кафедры или только курсы с
  активными зачислениями группы?
- [ ] Переопределяет ли студент `startTime`/`endTime` вручную, или всегда из `BellScheduleEntry`?
- [ ] Нужна ли визуальная отметка «новых» лекций в расписании студента после генерации?
- [ ] Как сообщать о неполном/устаревшем (относительно изменённых `Pair`) расписании — баннер
  «перегенерировать»?
- [ ] Что происходит при `DELETE /lectures/{id}`, если по лекции уже есть отметки посещаемости —
  нужно клиентское предупреждение, или бэкенд сам это блокирует?
