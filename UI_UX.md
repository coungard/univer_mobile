# UI_UX.md — генерация расписания/лекций «на ходу»

> Черновик от Claude: структура документа + рекомендации по UX для ключевой фичи продукта —
> генерация `Lecture` из шаблонов `Pair`. Разделы «Рекомендации» — предложения, разделы
> «Ожидаемое поведение» — здесь **владелец продукта описывает финальное решение**; там, где решение
> ещё не принято, оставлен явный вопрос вместо предположения.
>
> **Обновление:** цель продукта — чтобы **студент сам** заполнял циклическое расписание своей
> группы (`Pair`) и генерировал по нему `Lecture`, без участия `ADMIN`/`TEACHER` на каждом шаге.
> Это прямо конфликтует с текущим бэкендом (см. раздел 0) — решение зафиксировано: делаем это
> требованием к бэкенду, а не переобуваемся в рамках того, что API позволяет сегодня.

## 0. ⚠️ Требуется расширение бэкенда (RBAC) — блокер

Сейчас по `API.md` роль `STUDENT` **не может**:

| Действие | Эндпоинт | Кому разрешено сейчас |
|---|---|---|
| Создать/изменить/удалить `Pair` | `POST`/`PUT`/`DELETE /pairs` | `ADMIN` (`API.md:276-278`) |
| Создать `WeekScheduleCycle` | `POST /week-schedule-cycles` | `ADMIN` (`API.md:249`) |
| Сгенерировать `Lecture` (точечно или на семестр) | `POST /lectures/generate`, `/generate/semester/{id}` | `ADMIN`/`TEACHER` (`API.md:314-315`) |

Любой из этих вызовов от `STUDENT` сегодня вернёт `403`. Флоу ниже спроектирован **в расчёте на
то, что бэкенд откроет часть этих действий роли `STUDENT`** — это прямой запрос к бэкенд-команде
(репозиторий `coungard/univer`, вне скоупа мобильного репо), не то, что можно сделать только
клиентскими изменениями.

**Рекомендуемый (минимальный, а не максимальный) объём расширения:**

- ✅ Открыть `STUDENT` **`POST`/`PUT`/`DELETE /pairs`** — но **со скоупом**: студент может писать
  только `Pair`, где `groupIds` содержит его собственный `groupId` (взятый из `sub` JWT →
  `Student.groupId`, как и в `GET /lectures/me`). Проверка должна быть на бэкенде, а не только
  скрытием поля в UI — иначе любой авторизованный студент сможет отредактировать расписание чужой
  группы, просто дёрнув API напрямую.
- ✅ Открыть `STUDENT` генерацию лекций — но см. пункт про `generate/semester` ниже, там сама
  семантика эндпоинта не подходит для скоупинга по группе «из коробки».
- ❌ **Не открывать** `POST /week-schedule-cycles` студенту в первой версии. `WeekScheduleCycle` —
  контейнер на весь семестр (`GET /week-schedule-cycles/semester/{semesterId}` возвращает
  **один** объект, не `Page` — `API.md:247` — то есть модель предполагает один цикл на семестр).
  Если разрешить создавать циклы студентам, ничего не мешает получить дубли на один семестр без
  явной защиты от гонки. Проще и безопаснее оставить создание цикла в зоне `ADMIN` (разово при
  открытии семестра), а самим студентам открыть только заполнение `Pair` внутри уже существующего
  цикла.

**Ожидаемое поведение (заполнить):** _согласны с таким минимальным скоупом, или нужно продавить
и self-service создание цикла тоже (например, «первый студент группы, зашедший в раздел
расписания, автоматически получает цикл создаваемым по своему семестру» — тогда бэкенду нужна
идемпотентная `get-or-create` семантика, которой сейчас нет)?_

### 🔴 Риск, который стоит решить до реализации: нет проверки конфликтов между группами

`Pair.groupIds` — массив, то есть один `Pair` в принципе может обслуживать несколько групп сразу
(поток/совместная лекция). Но если **каждая группа сама** заполняет свои `Pair` независимо, а
бэкенд не проверяет пересечения — ничто не мешает двум студентам из разных групп независимо
поставить одного и того же `teacherId` на один и тот же `dayOfWeek`+`pairNumber`+`weekParity`, но
в разных аудиториях (преподаватель физически не может вести оба), либо одну и ту же `room` для
двух разных занятий одновременно. `API.md` не описывает никакой валидации конфликтов на уровне
`Pair`. Три опции:

1. Бэкенд добавляет валидацию (teacher/room double-booking check) при `POST/PUT /pairs` — чище
   всего, но это тоже бэкенд-работа, не только UI.
2. Клиент варнит «мягко» (проверяет по уже загруженным `Pair` того же `weekScheduleCycleId» и
   показывает предупреждение перед сохранением), но не блокирует — конфликт всё равно возможен
   при гонке двух студентов, сохраняющих одновременно.
3. Ничего не делаем в MVP, полагаемся на то, что расписание малых групп физически редко
   пересекается — риск принимается сознательно.

**Ожидаемое поведение (заполнить):** _какая из трёх опций (или комбинация) устраивает на старте?_

## 1. Контекст: что вообще «генерируется»

Бэкенд различает две сущности (см. `API.md:104-136`):

- **`Pair`** — шаблон повторяющегося занятия в циклическом расписании семестра (`WeekScheduleCycle`):
  день недели + чётность недели (`ODD`/`EVEN`/`BOTH`) + номер пары + курс + преподаватель + аудитория +
  группы. Это «расписание» в привычном понимании — таблица «когда и что».
- **`Lecture`** — конкретное занятие на конкретную дату/время. Это то, что видит студент
  (`GET /lectures/me`) и то, по чему отмечается посещаемость.

Между ними нет автосвязи. `Lecture` появляются только явным действием:

| Действие | Эндпоинт | Свойства |
|---|---|---|
| Одна лекция на одну дату из шаблона | `POST /lectures/generate` (`GenerateLectureRequest{pairId, date}`) | `date` должна соответствовать `dayOfWeek`/`weekParity` пары; **идемпотентность точечного вызова не задокументирована** — см. открытый вопрос в разделе 6 |
| Весь семестр разом | `POST /lectures/generate/semester/{weekScheduleCycleId}` | генерирует по **всем** `Pair` цикла (всех групп, не только одной) в границах `Semester.startDate…endDate`; **идемпотентно** — уже сгенерированная пара `Pair+дата` молча пропускается |
| Вручную, без шаблона | `POST /lectures` (`LectureDto`) | `sourcePairId` не заполняется — полностью ручное занятие (замена, доп. пара, отработка) |
| Редактирование/отмена одной лекции | `PUT /lectures/{id}` / `DELETE /lectures/{id}` | точечная правка после генерации |

«Генерация на ходу» в терминах продукта = студент в любой момент семестра заполняет шаблон
`Pair` своей группы и одним действием превращает его в реальные занятия в своём расписании — без
ручного ввода каждой даты и без похода к администратору/преподавателю.

## 2. Роли и точки входа

| Роль | Что делает | Скоуп |
|---|---|---|
| **Student** (основной сценарий этого документа) | Заполняет `Pair` для **своей группы** внутри уже существующего цикла семестра; генерирует `Lecture` по этим `Pair` | Только свой `groupId` |
| **Teacher** | То же самое, но по своим курсам (`teacherId`) — как раньше в `ROADMAP.md` Фазе 6, актуально для случаев, когда студенты группы это не сделали или нужна правка | Свои `Pair` (по `teacherId`) |
| **Admin** | Создаёт `WeekScheduleCycle` на семестр (см. раздел 0), может редактировать/удалять любой `Pair`, разруливает конфликты | Без ограничений |

**Ожидаемое поведение (заполнить):**
- _Заполняет расписание **любой** студент группы, или это делает один назначенный представитель
  («староста»)? Если любой — при одновременном редактировании двумя студентами одной группы кто
  выигрывает (last-write-wins через `PUT`, или нужна какая-то блокировка/уведомление «уже
  редактируется»)?_
- _Может ли Teacher менять `Pair`, который завёл студент (и наоборот)? Если да — как показать
  «кто последний менял» (`API.md` не даёт `updatedBy` для `PairDto`, только `id`/поля шаблона —
  если нужна атрибуция, это тоже бэкенд-доработка)._

## 3. Принципы UX для генерации (рекомендации)

1. **Предпросмотр перед коммитом.** Перед вызовом генерации на семестр показать сводку: диапазон
   дат семестра, число заполненных студентом `Pair`, оценочное число лекций. Кнопка
   «Сгенерировать» — осознанное действие.
2. **Явно сообщать про идемпотентность там, где она подтверждена.** `generate/semester`
   безопасно вызывать повторно (`API.md:326-327`) — снять тревожность «а вдруг задвою». Для
   точечного `POST /generate` такой гарантии в `API.md` нет — пока не подтверждено бэкендом,
   в UI **не обещать** пользователю безопасный повтор для этого пути (см. раздел 6).
3. **Заполнение — обычный CRUD-экран, не мастер на один раз.** Студент должен иметь возможность
   вернуться и что-то поправить: перенести пару, поменять аудиторию, удалить дубль. Список `Pair`
   своей группы — редактируемая таблица «день × номер пары», а не разовая форма.
4. **Генерация — отдельный явный шаг после заполнения**, не автоматический побочный эффект
   сохранения `Pair`. Студент должен успеть заполнить несколько пар, посмотреть на них вместе, и
   только потом нажать «Сгенерировать занятия на семестр».
5. **Прогресс и ошибки.** `generate/semester` — потенциально небыстрый запрос. Показать индикатор
   ожидания с понятным текстом, а не спиннер на пустом экране. При сетевой ошибке — состояние
   «не удалось сгенерировать, попробовать снова».
6. **Явно объяснять эффект `generate/semester` на другие группы**, если он остаётся общим на весь
   цикл (см. риск в разделе 0/6): текст вида «это действие также создаст занятия для других
   Pair-шаблонов в этом цикле, если они есть» — либо, если бэкенд добавит скоупинг по группе,
   этот пункт снимается.

## 4. Флоу «Студент сам заполняет расписание» (основной сценарий)

```
Таб «Расписание» (пусто, группа назначена, лекций нет)
     │
     ├─ Цикл на семестр не создан (GET /week-schedule-cycles/semester/{semesterId} → 404)
     │     → пустое состояние «расписание семестра ещё не открыто администратором,
     │        обратитесь к администратору» (блокер вне контроля студента, см. раздел 0)
     │
     └─ Цикл существует, Pair моей группы нет
           → CTA «Заполнить расписание группы»
                 │
                 ▼
        Экран «Расписание группы» — таблица день недели × номер пары
        (только Pair, где groupIds содержит мой groupId)
                 │
                 ├─ [+ Добавить занятие] → форма:
                 │     день недели, чётность (ODD/EVEN/BOTH), номер пары,
                 │     курс (из списка зачислений/курсов группы), преподаватель
                 │     (авто из Course.teacherId, редактируется?), аудитория,
                 │     время (по умолчанию из BellScheduleEntry университета —
                 │     не переопределять вручную, см. вопрос ниже)
                 │     → мягкая проверка конфликта с уже заполненными Pair группы
                 │     → POST /pairs
                 │
                 ├─ Pair → [Изменить] → PUT /pairs/{id}
                 ├─ Pair → [Удалить] → DELETE /pairs/{id}
                 │
                 └─ [Сгенерировать занятия на семестр] (доступно, когда заполнена
                    хотя бы одна пара) → предпросмотр (сколько Pair, диапазон дат,
                    предупреждение про другие группы цикла — см. раздел 3.6)
                    → подтверждение → POST /lectures/generate/semester/{cycleId}
                    → результат: «Готово, расписание появится в разделе
                       “Расписание” у всех студентов группы»
```

**Ожидаемое поведение (заполнить):**
- _Курс для `Pair.courseId` — студент выбирает из **всех** курсов кафедры/университета
  (`GET /courses`), или только из тех, на которые уже есть зачисление у кого-то из группы
  (`Enrollment`)? Если из всех — где в UI ограничение, чтобы студент случайно не завёл занятие по
  курсу, на который никто не зачислен?_
- _Разрешаем ли студенту переопределять `startTime`/`endTime` пары вручную, или всегда наследуем
  из `BellScheduleEntry` по `pairNumber` (безопаснее — меньше шанс развалить сетку звонков
  университета)?_
- _Что показываем вместо CTA «Заполнить расписание группы», если у самого цикла нет ни одной
  группы с уже готовым расписанием, на которое можно ориентироваться (совсем новый семестр)?_

## 5. Флоу Teacher/Admin (вторичный путь, правка и подстраховка)

Остаётся как в `ROADMAP.md` Фазе 6–7 — преподаватель/администратор видит те же `Pair` (в т.ч.
заведённые студентами) и может их поправить или сгенерировать лекции сам, если группа этого не
сделала вовремя.

```
Мои курсы → Курс → «Расписание курса» (список Pair цикла, включая заведённые студентами)
                          │
                          ├─ [Сгенерировать на семестр] → Предпросмотр → Подтверждение → Результат
                          │
                          └─ Pair → [Сгенерировать одну дату] → выбор даты
                                                                       → создана Lecture

Мои лекции (плоский список, все сгенерированные + ручные)
     │
     ├─ Lecture → [Редактировать] (room/time/content) → PUT
     ├─ Lecture → [Отменить занятие] → DELETE (с подтверждением)
     └─ [+ Добавить занятие вручную] → POST /lectures (sourcePairId не задан)
```

## 6. Пустые/промежуточные состояния (студент)

Обновлено с учётом self-service (было: `src/features/schedule/ScheduleScreen.tsx`, только два
состояния — «нет группы» / «лекций нет, ждите»):

| Состояние | Причина | Что показываем |
|---|---|---|
| Нет группы | `student.groupId == null` | как раньше: «группа ещё не назначена, обратитесь к администратору» |
| Есть группа, цикла семестра нет | `GET /week-schedule-cycles/semester/{semesterId}` → 404 | «расписание семестра ещё не открыто, обратитесь к администратору» — студент здесь ничего сделать не может |
| Есть группа и цикл, `Pair` моей группы нет | `GET /pairs/group/{groupId}` пуст | CTA «Заполнить расписание группы» (раздел 4) — активное действие, а не ожидание |
| `Pair` заполнены, `Lecture` нет | генерация ещё не запускалась | CTA «Сгенерировать занятия на семестр» прямо в табе «Расписание», не только на экране заполнения |
| `Pair` заполнены частично относительно `Semester.endDate` | последняя `Lecture` раньше конца семестра, а `Pair` покрывают более поздние даты (сгенерировано не после последнего изменения `Pair`) | баннер «расписание могло измениться — перегенерировать?» (эвристика на клиенте, т.к. бэкенд не даёт признака «актуальности» генерации) |

## 7. Открытые вопросы (требуют решения перед реализацией)

### Бэкенд (блокеры)
- [ ] Открыть `STUDENT` доступ к `POST`/`PUT`/`DELETE /pairs`, со скоупом по своему `groupId`,
  проверяемым на бэкенде (не только в UI).
- [ ] Открыть `STUDENT` доступ к генерации лекций — и решить, как скоупить
  `generate/semester/{weekScheduleCycleId}` по группе (сейчас генерирует по **всем** `Pair`
  цикла, а не только заполненным конкретной группой): либо новый параметр/эндпоинт
  `generate/semester/{id}?groupId=...`, либо клиент отдельно перебирает точечный
  `POST /generate` по всем валидным датам своих `Pair` (тяжелее, и требует ответа на следующий
  пункт).
- [ ] Подтвердить идемпотентность точечного `POST /lectures/generate` (по аналогии с
  `generate/semester`) — сейчас в `API.md` это не задокументировано, а без этого повторный клик
  «Сгенерировать» на точечном пути может дать дублирующую ошибку вместо тихого пропуска.
- [ ] Решить риск отсутствия проверки конфликтов teacher/room между `Pair` разных групп одного
  цикла (раздел 0) — валидация на бэкенде vs мягкий варнинг на клиенте vs осознанно не делаем.
- [ ] Решить, остаётся ли `POST /week-schedule-cycles` только у `ADMIN`, или тоже открывается
  студентам с `get-or-create`-семантикой (раздел 0).

### Продукт/UX
- [ ] Любой студент группы или только представитель («староста») может редактировать расписание
  группы?
- [ ] Источник списка курсов при заполнении `Pair` — все курсы кафедры или только курсы с
  активными зачислениями группы?
- [ ] Переопределяет ли студент `startTime`/`endTime` вручную, или всегда из `BellScheduleEntry`?
- [ ] Нужна ли визуальная отметка «новых» лекций в расписании студента после генерации?
- [ ] Как сообщать о неполном/устаревшем (относительно изменённых `Pair`) расписании — баннер
  «перегенерировать»?
- [ ] Что происходит при `DELETE /lectures/{id}`, если по лекции уже есть отметки посещаемости —
  нужно клиентское предупреждение или бэкенд сам это блокирует?
